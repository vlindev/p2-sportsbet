Dual-Channel Betting System — Information Flow

Brainstorm visualization. Two input channels, one system of record, one bookkeeper overseeing everything.

How Two Paths Arrive at the Same Place

Lane A — Self-Service

Member opens the system directly.
Views matches, places bet, confirms.

Lane B — Line Group Chat

Member sends bet via Line message.
Same as today. Nothing changes for them.

Direct Write

Bet saved to database immediately.
Tagged: source = member

Bookkeeper Enters

Reads Line message, enters bet into system on behalf of member.
Tagged: source = bookkeeper

Same database, same table, same row format
One System of Record

All bets — regardless of how they entered — live in the same place.
Settlement engine treats them identically.
The source tag is metadata, not logic.

Bookkeeper Dashboard

Sees ALL bets from both channels in one view.
Can verify, edit, delete, flag duplicates.
Role: auditor + safety net, not data entry.

Settlement Engine

Reads all valid bets. Calculates pool payouts.
Applies rake. Produces monthly settlement.
Doesn't know or care about the source.

The Core Architectural Insight

The system doesn't have "two modes." It has one mode with two doors.

A bet placed by a member at 10pm on Sunday and a bet entered by the bookkeeper from a Line message at 10:05pm are the same row in the same table. The only difference is a source field that says who created it.

Settlement, reports, payouts — none of them read the source field. It exists purely so the bookkeeper can see what came from where when reviewing.

System

Bookkeeper
Glances at dashboard. Sees 陳先生's bet flagged as self-placed. Amount and team look right. No action needed. Moves on.

林大哥 — The Holdout (Lane B)

System
Bet saved. Identical to 陳先生's bet in every way except the source tag. Settlement engine will treat them exactly the same.
3

王太太 — The Mistake Maker (Lane A → Bookkeeper Fixes)

Sun 7:00pm
王太太 (on phone)
Opens system. Wants to bet on Match 5, Team A. Accidentally taps Team B and confirms. Realizes the mistake immediately. Panics. Calls the bookkeeper.
Sun 7:05pm
Bookkeeper
Gets the call. Opens dashboard. Finds 王太太's bet on Match 5. Sees it was self-placed 5 minutes ago. Edits team from B → A. Done. Tells 王太太 it's fixed. Total time: 30 seconds.

This is the SAME interaction that happens today when someone sends a wrong bet in Line. The fix path is identical — call the bookkeeper. The system just makes the fix instant and traceable instead of "delete that message and resend."
4

週一 7pm — The Deadline (System Handles Stragglers)

Sun 6:55pm
Bookkeeper

Sun 7:00pm
System — Deadline
Cutoff hits. 8 members still haven't bet on some matches. System auto-places mandatory 1兩 bets for each missing match. source = auto_placed. All 85 members now have coverage on all 7 matches.

System — LIFO Check
After auto-placement, system checks if any matches need LIFO balancing. If yes, drops latest bets from over-subscribed side, marks is_valid = false. Pool model handles the rest — uneven sides are fine.

Bookkeeper

The Bookkeeper's Role — Before vs After

Before (Current Design)

  • x Read every Line message to find bets
  • x Manually enter every single bet into system
  • x Cross-reference chat history when disputes arise
  • x Calculate or verify all settlement numbers
  • x Answer "did you get my bet?" messages
  • x Be the only person who knows the current state
  • x Enter match results + all bet consequences

After (Dual-Channel)

  • + Enter bets ONLY for Lane B members (Line holdouts)
  • + Review self-placed bets — spot-check, not re-enter
  • + Fix mistakes when members call (same as today)
  • + Enter match results (unchanged)
  • + Monitor dashboard: 85/85 coverage before deadline
  • + Settlement is fully automated — verify, don't calculate
  • + Disputes answered by system record, not memory

Data Collision Risks — What Could Go Wrong

Three scenarios where dual-channel input could cause problems, and how each is resolved.

Medium Risk

Duplicate Bet

Member places bet in system AND sends Line message. Bookkeeper enters the Line bet without realizing member already self-placed.
Resolution: Bookkeeper dashboard shows existing bets per member per match. Before entering a Line bet, bookkeeper sees "陳先生 already has a bet on this match (self-placed)." Duplicate prevented at the UI level.
Low Risk

Contradictory Bet

Member bets Team A in system, then messages "actually Team B" in Line chat.
Resolution: Bookkeeper sees both: the system bet (Team A) and the Line message (Team B). Edits the existing bet. One bet per member per match is enforced — no collision possible, just an edit.
Low Risk

Timing Edge Case

Member places bet at 6:59pm. Bookkeeper is simultaneously entering a Line bet for the same member at 6:58pm. Both write at nearly the same time.
Resolution: Database constraint: one bet per member per match. Second write either fails (shows error) or bookkeeper sees the duplicate immediately. No silent corruption.

The Gravity Model — Why You Don't Force Migration

Month 1
10% self-place bets
90% via Line → bookkeeper

Bookkeeper workload: ~same as today
Month 3
40% self-place bets
60% via Line → bookkeeper

Bookkeeper workload: noticeably lighter. Members talk about checking the system between holes.
Month 6
70% self-place bets
30% via Line → bookkeeper

Bookkeeper role is mostly oversight. The holdouts are permanent — and that's fine.
